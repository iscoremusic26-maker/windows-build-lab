# CP10.6A — implementation and evidence (Dusklight 40457c6)

## 1. Source of the visual state
The visual layer reads the approved CP10.6 record (`devf_dyn::Entry`): Blue aura target = `group`, Black aura and eyes target = `fury > 0`. It never recomputes gameplay and adds no hook (still ONE `daE_OC_c::execute` PRE/POST pair; `dynamic_post()` calls `visual_post()` right after the logic step). Because it only follows `group` / `fury`: the HP initialisation (220 -> 440, 220 -> 150), regeneration, stagger and lethal hits cannot start anything (they never set `fury`), a renewal changes nothing (`fury` stays > 0), and a pair that is not owned (third party touched the colliders) has `group = fury = 0`, so no visual either.

## 2. Aura: resource choice
**Chosen:** `ID_ZF_J_FAIRY00_GLOW` (0x072F), common particle bank (no 0x8000 bit, bank 0).
- It is the glow the game itself shows around the fairy in Link's bottle (`d_a_alink_effect.inc` L1675-1685), spawned with the very idiom used here: `dComIfGp_particle_set(key, id, &pos, &tevStr, ...)` then `dComIfGp_particle_getEmitter(key)`, one refresh per tick. The common bank is loaded for the whole game, so unlike scene-bank resources it does not depend on the stage.
- Colour and alpha are applied per emitter after the call (`setGlobalPrmColor/EnvColor/Alpha/Scale`), as `d_a_kytag03.cpp` L311-362 does every frame. JPA multiplies the particle colour by the emitter's global colour and alpha (`JPABaseShape.cpp` L25-37), so a pale glow is tinted by it and alpha gives the fade. The game itself fades such emitters by lowering `setGlobalAlpha` per frame (`setSwordChargeEffect`, -17 per frame).
- **Cleanup is native:** `dPa_control_c::level_c::execute` removes a level emitter that was not refreshed during the frame (`d_particle.cpp` L971-984, `cleanup()` L937-955). We only keep a `u32` key; a dead actor, a room exit or an unload simply stops refreshing and the engine cuts it. On fade completion we also call `stopDrawParticle()`. A stale key can never match a newer emitter (ids are unique and monotonic).
- **Imports added (reviewed, present in the official SDK import library):** `dComIfGp_particle_set` (12-argument keyed form), `dComIfGp_particle_getEmitter`, `JPAResourceManager::getResource`, data `dPa_control_c::mEmitterMng`. The last two serve a once-per-session existence probe: `dPa_control_c::set` reads the resource's user work before checking that it exists, so the resource is looked up first and rejected cleanly (`AURA_RESOURCE_MISSING_FROM_COMMON_BANK`) if absent. All emitter setters are header inlines (no import).
- **Discarded:** (a) scene-bank `0x84ED` (CP04.3 marker): depends on the stage's scene bank, never human-verified, and needed a hand-built emitter factory with a strict key/curve guard; (b) the Link sword-charge sparkle `ID_ZI_J_SWA_KIRARI_A`: shaped for a sword, needs a sword matrix; (c) Puppet-Zelda / sword-aura scene effects (`PZ_BODYAURA`, `VA_KENAURA`): scene bank, other stages; (d) `ID_AK_JN_AURA*` (common bank, body/head/limbs aura): the source never spawns them, so how they expect to be attached is unknown; (e) tinting the model materials or drawing a second model: paint-like look, new draw hooks; (f) our own particle data: not "reuse".
- **Not verified:** that the glow looks good tinted blue/purple at the chosen scale (4.0 / 4.4) and alpha (110 / 130), or its exact shape and brightness. Position = middle of the body (`current.pos` to `eyePos`), refreshed every tick so it follows the actor.
- **Bounds:** at most 8 simultaneous aura emitters (`kMaxAuras`, a 9th is rejected cleanly), refreshed once per tick each; the engine pool is shared, so a pool failure is a clean rejection too.

## 3. Black eyes
The three E_OC2 materials share one 128x128 CMPR atlas; the eye material samples only its own region (the green-iris area), and the approved FIX01 body texture is bound to body packets 0 and 1 only. For the eyes `eye_recolor.hpp` builds **seven private variants** (t = 1/7 ... 7/7) of the original atlas on caller-owned copies: only greenish endpoints (hue 70-170 deg, chroma >= 12-32) are moved towards purple keeping their luminance, in the compressed domain (RGB565 endpoints, indices kept, block mode preserved), integer-only (golden vectors identical on MSVC/GCC). A variant is bound to the **eye packet of that Black only** (`J3DMatPacket::setTexture`, the same call the body binding uses); variant 0 is the native texture.
- The fade swaps the packet's texture only when the variant index changes (7 swaps per fade-in, never per tick). Fade-out walks back down to the native texture.
- **Ownership:** before every swap the packet must hold exactly the texture this module put there (native, or the variant it set last), the model must be the one bound at admission, and the material must be the model data's eye material; otherwise `BLACK_VISUAL_REJECTED part=EYES` and nothing is written (no restore over a foreign texture either). A read-back after each write restores the previous texture on mismatch.
- The variants are prepared at Black admission (never during combat). If the atlas contains no green endpoints (the recolor would change nothing) the eyes are disabled and logged (`BLACK_EYES_UNAVAILABLE`), the body texture is untouched.
- Why the whole atlas may be processed: the variant is only ever drawn through the eye packet. Other greens elsewhere in the atlas are never sampled through it.
- **Not verified:** the actual eye pixels (the hue window was chosen from the structure of the atlas, not tuned on screen). The log shows `BLACK_EYES_PREPARED` (variants built), `BLACK_EYES_ON/OFF` (swaps happened) and `BLACK_EYES_UNAVAILABLE` (no green found); only your eyes can say how it looks.

## 4. State machine (`visual_policy.hpp`, pure, templated over an `Fx` adapter)
Level 0..100 per channel; target on: +10 per tick; off: -7 per tick (10 ticks in, 15 out). State = f(level, target): INACTIVE / FADING_IN / ACTIVE / FADING_OUT. A level never restarts: re-targeting continues from the current level. The aura emitter is created on the first level > 0, refreshed on every tick while level > 0 (required to keep it alive), released at level 0. Eye variant = rounded `level * 7 / 100`. A failure of the aura or of the eyes marks only that channel as faulted for this generation (no retries, one log line); the other keeps working.

## 5. Logs (bounded: 24 per actor, 400 per session, only on transitions)
`DEVF_CP10_6A_VISUAL event=BLUE_VISUAL_ON | BLUE_VISUAL_OFF | BLUE_VISUAL_REJECTED | BLACK_VISUAL_ON | BLACK_VISUAL_OFF | BLACK_VISUAL_REJECTED | BLACK_EYES_ON | BLACK_EYES_OFF | VISUAL_RELEASED | VISUAL_CLEANUP | AURA_RESOURCE_OK` with actor id, generation, variant, source, encounter, part (AURA/EYES), state, level, alpha, eye variant (of 7), resource id and bank, emitter key, scale, rgb, reason, `visual_pixels=HUMAN_RUNTIME_PENDING`. `BLACK_VISUAL_REFRESH` is deliberately not logged: a renewal changes nothing visually (see the logic line `BLACK_FURY_REFRESH`). Existing `DEVF_CP10_6_DYNAMIC`, `DEVF_CP10_5_DAMAGE`, `DEVF_CP10_4_VARIANT`, `DEVF_CP10_3_REGEN`, `HP_APPLIED` and `BLACK_TEXTURE_*` lines are unchanged.

## 6. Unload and release
`visual_shutdown()` (before `black_shutdown()`): for each record, every aura is stopped (`stopDrawParticle`, then nobody refreshes it, so the engine removes it); the eye packet is restored to the native texture only if the actor is still live (same id, same address, `init_state != 3`) and the packet still holds our texture. A gone actor is not touched at all. `VISUAL_RELEASED` is logged when an actor disappears (room exit, destruction, id reuse): no packet, model or texture is touched; the emitter expires by itself within one tick.

## 8. Not verified
Everything visual; whether the engine pool or an event (cutscene) interacts with the emitter; other mods that hook `daE_OC_c::execute`, change materials or particles; the Black eye region of the real atlas; behaviour at different resolutions or with the Dusklight interpolation on/off beyond what the approved body texture already showed.
